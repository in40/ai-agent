## 1 Область применения

Представленный в настоящих рекомендациях протокол IP/Ill предназначен для защиты IP-пакотов при их передаче через канал связи. Защита IP-пакотов заключается в обеспечении имитологии пакетов, а также опциональном обеспечении конфиденциальности пакетов. Для этих целей при использовании инкапсулированных IP-паков и служебной информации источников, а также IP-паков с высоким уровнем шифрования пакетов для инкапсуляции пакетов. Протокол IP/Ill также допускает возможность организации защиты от навязывания передававшихся ранее пакетов на основе использования значений счетчика и/или меток времени.

Протокол IP/Ill может применяться для создания виртуальных частных сетей (Virtual Private Network) на 3-м (сетевом) уровне базовой эталонной модели ISO OSI. Защита данных осуществляется при передаче IP-пакотов между любой парой узлов, поддерживающих протокол IP/Ill, включая варианты взаимодействия двух конечных узлов, конечного узла и шлюза безопасности и двух шлюзов безопасности. Все механизмы защиты реализуются в режиме без установления соединения (в сетевом смысле) между двумя взаимодействующими узлами.

3 Термники, определения и обозначения



3.1 Термины и определения


В настоящих рекомендациях применены следующие термины с соответствующими определениями:

3.1.1 AEAD (Authenticated Encryption with Associated Data): Шифрование с имитозацией и ассоцированными данными.

3.1.2 IP-пакет (сетевой пакет): Логически неделимый блок данных на сетевом уровне базовой эталонной модели ISO OSI, относящийся к протоколу IP.

3.1.3 IPllr-пакет: IP-пакет, защищенный с использованием IPllr-проотокола.

3.1.4 IPllr-сообщение: Данные, передаваемые в теле IPllr-пакета.

3.1.5 гаммирование: Процесс наложения по определенному закону гамми шифра на открытые данные.

3.1.6 имитозвистка: Строка бит фиксированной длины, полученная применением симметрично-криптографического метода к сообщению для обеспечения его целостности и аутентификации источника.

3.1.7 исходный IP-пакет: IP-пакет до его защиты протоколом IPllr.

3.1.8 ключ: Изменяемый параметр в виде последовательности символов, определяющий криптографическое преобразование.

3.1.9 ключ обмена: Ключ, известный только заданной паре узлов, используемый для выработки производных ключей.

3.1.10 ключевая система: Совокупность множества ключей, подсистемы установки таких ключей и подсистемы управления ими.

3.1.11 криптографический набор (криптонабор): Совокупность криптографических алгоритмов и параметров, используемых в IPllr-проотоколе.

3.1.12 контекст сетевого узла: Информация, необходимая для обработки/создания IPllr-пакетов от/для сетевого узла, логически связанного с данными.

3.1.13 маршрутизация IPllr-пакетов: Функция пересылки IPllr-пакетов, выполняемая сетевым узлом при приеме IPllr-пакетов, которые адресуют данному сетевому узлу с точки зрения IP-проотокола, но для которых он не является узловолучателем.

3.1.14 политика приема IPllr-пакетов: Совокупность правил обработки входящих IPllr-пакетов.

3.1.15 политика безопасности: Совокупность правил обработки IP-трафика сетевым узлом.

3.1.16 производный ключ: Ключ, выработанный из исходного ключа и открытых случайных и/или фиксированных данных.

3.1.17 режим работы протокола IPllr: Один из трех режимов работы протокола IPllr: транспортный, «легкий» туннель и туннель криптографического метода.

3.1.8 симметричный криптографический метод: Криптографический метод, использующий один и тот же ключ для преобразования, осуществляемого отправителем, и для преобразования, осуществляемого получателем.

3.1.9 синхронизация: Комбинация знаний, передаваемая по каналу связи и предназначенная для инициализации криптографических алгоритмов.

3.1.20 сквозная имитозащита: Имитозащита, осуществляемая между узлом-отправителем и узлом-получателем.

3.1.21 транзитная имитозащита: Имитозащита, осуществляемая между парами соседних узлов в цепочке передачи пакета.

3.1.22 транзитный узел: Узел, выполняющий функцию маршрутизации IPllr-пакетов.

3.1.23 узел (сетевой узел): Сетевое устройство, имеющее уникальный идентификатор и поддерживающее протокол IPllr.

**3.2 Обозначения**

В настоящих рекомендациях используются следующие обозначения:

$V^*$
— множество всех двойных строк конечной длины, включая пустую строку;

$x ||$
— длина (число компонент) строки $x \in V^*$;

$V_s$
— множество всех двойных строк длины $s$, где $s$ — целое неотрицательное число; номерация подстрока и компонент строки $V_s$ осуществляется справа налево, начиная с нуля;

$x \| y$
— конкатенация двойных строк $x$ и $y$ из $V^*$, т. е. строка из $V_{|x|+|y|}$, в которой лева подстрока из $V_{|x|}$ совпадает со строкой $x$, а правая подстрока из $V_{|y|}$ совпадает со строкой $y$;

$0^r$
— двойная строка, состоящая из $r$ нулей;

$LSB_s(x)$
— усечение двойной строки $x$ длины $m$, $m \ge s$, до двойной строки длины $s$, выполняющееся по правилу: $LSB_s(x_{m-1} \| ... \| x_1 \| x_0) = x_{s-1} \| ... \| x_1 \| x_0, x_i \in V_1, i=0,1,...,m-1$;

$IntToVec_s(x)$
— представление элемента кольца $x \in \mathbb{Z}_2^s$ в виде двойной строки длины $s$: для $x = x_0 + 2x_1 + ... + 2^{s-1}x_{s-1}$, где $x_i \in V_1, i=0,1,...,s-1$, выполнено равенство $IntToVec_s(x) = x_{s-1} \| ... \| x_1 \| x_0$;

$CharToByte(c)$
— представление символа $c$ в виде двойной строки длины 8, выполняющееся по следующим правилам: $CharToByte(c) = 0 \| IntToVec_7(ASCII(c))$, где $ASCII(c) \in \mathbb{Z}_{2^7} — ASCII-представление символа $c$;

$StrToVec_s(string)$
— представление символьной строки string = '$_{m-1}c_{m-2}...c_0'$, состоящей из $m$ символов, в виде двойной строки длины $s$, где $s \ge 8\cdot m$, выполняющееся по правилам: $StrToVec_s('$_{m-1}c_{m-2}...c_0'$) = $0^{s-8}\cdot m \| CharToByte(c_{m-1}) \| ... \| CharToByte(c_0)$;

$K_{ENC}$
— ключ шифрования пакета. Длина значения определяется используемым криптографическим набором;

$K_{MAC}$
— ключ свозной имитозащиты пакета. Длина значения определяется используемым криптографическим набором;

$K_{Aead}$
— ключ шифрования и свозной имитозащиты пакета. Длина значения определяется используемым криптографическим набором;

$K_{TMAC}$
— ключ транзитной имитозащиты пакета. Длина значения определяется используемым криптографическим набором;

Version
— версия IP-Illir-заголовка. Текущий документ описывает IP-Illir-заголовок, для которого Version = 1. Длина поля равна 8 бит;

CS
— идентификатор криптографического набора, определяющий состав криптографических механизмов и их параметров, используемых при создании IP-Illir-пакета. Длина поля равна 8 бит;

T
— флаг наличия поля для транзитной имитозащиты. Если $T = 1$, то в IP-Illir-заголовке присутствуют поля TransitIdentifier, TransitIntegrityCheckValue и TransitInValue, иначе поле отсутствует. При вычислении и проверке свозной имитозащиты (ICV) в поле T необходимо подставить 0. Длина поля равна 1 бит;

D
— флаг наличия поля DestinationIdentifier. Если D = 1, то в заголовке присутствует поле DestinationIdentifier, иначе поле отсутствует. Идентификатор узел-получателя необходим при маршрутизаторах IP-Illir-пакетов. Длина поля равна 1 бит;

ExtID
— флаг расширенных идентификаторов сетевых узлов. Если ExtID = 0, то все идентификаторы сетевых узлов (поле SourceIdentifier и, при наличии, поле DestinationIdentifier и TransitIdent) имеют длину 32 бит. Если ExtID = 1, то все идентификаторы сетевых узлов имеют длину 64 бит. Длина поля равна 1 бит;

TKN
- номер ключа обмена, который использовался для вычисления транзитной имитовставки. Если транзитная имитозащита не используется, т. е. T = 0, то поле должно иметь значение 0. Timestamp
- время отправки пакета. Поле содержит значение времени отправки по астрономическим часам узла-отправителя в POSIX-формате времени, уменьшенное на 0x40000000 с. Время пополнения поля оценивается 2140 годом. Длина поля равна 32 бит;

SourceIdentifier
- идентификатор сетевого узла-отправителя, с помощью которого узел-получатель определяет отправителя IPllr-пакета и связанный с ним контекст узла-отправителя для обработки пакета. Длина поля равна 32 бит при ExtID = 0 или 64 бит при ExtID = 1;

DestinationIdentifier
- идентификатор сетевого узла-получателя, необходимый при маршрутизации IPllr-пакетов. Поле присутствует, если D = 1. Длина поля равна 32 бит при ExtID = 0 или 64 бит при ExtID = 1;

SequenceNumber
- порядковый номер пакета; бессназковое целое. Длина поля равна 32 бит при ExtSN = 0 или 64 бит при ExtSN = 1;

InitValue (IV)
- сквозная синхроносылка, которая может использоваться при выполнении операций шифрования и выработки сквозной имитовставки, а также для формирования произведенных ключей для этих операций. Длина поля определяется используемым криптографическим набором;

Type, Length, Value
- кортежи полей (тип, длина, значение), позволяющие передавать дополнительную информацию в составе IPllr-пакета. Type — тип значения, содержащегося в поле Value. Длина поля равна 8 бит. Length — байтовая длина поля Value. Длина поля равна 8 бит. Value — произвольные данные типа Type;

PayloadData
- поле переместной длины, содержащий исходный IP-пакет или его часть, в зависимости от режима работы IPllr-протокола;

Staffing
- сетевое дополнение IPllr-пакета, позволяющее обеспечить необходимую длину IPllr-сообщения для его более эффективной обработки. Поле Staffing заполняется последовательно целыми числами, представленных в двоичном виде: в первый байт помещается цифра 1, во второй — 2 и т. д. Длина значения определяется поле staffing SL, если SL отсутствует (S = 0) или имеет значение 0, то поле Staffing отсутствует;

SL
- число байт сетевого дополнения Staffing. Поле присутствует, если S = 1. Длина поля равна 8 бит;

Mode
- режим, в котором сформирован IPllr-пакет. Длина поля равна 2 бит;

5.1 Фрагментация IP- и IPlir-пакетов

Протокол IP при упаковке данных в IP-пакетах может фрагментировать (разбивать на части) сообщение вышележащих протоколов транспортного уровня UDP, TCP и др. После упаковки будет получено несколько (связанных) IP-пакетов, каждый из которых называется IP-фрагментом.

IPlir-протокол в транспортном режиме и режиме легкого тоннеля должен применяться только к целым (нефрагментированным) IP-пакетам, но не к IP-фрагментам. В туннельном режиме IPlir-протокол может применяться как к целым IP-пакетам, так и к IP-фрагментам.

При инкапсуляции в IPv4, IPlir-пакет, как и любой другой IPv4-пакет, в процессе передачи по сети может быть фрагментирован маршрутизаторами. До обработки IPlir-пакета на стороне узла-получателя или транзитного узла должна быть проведена дефрагментация такого IPlir-пакета.

### 6.1 Шифрование и имитозащита

Для обеспечения конфиденциальности пакета в протоколе IPlir предусмотрена возможность его шифрования с использованием симметричного криптографического метода. Шифрование пакета в IPlir рекомендуется, но не является обязательным. Отключение шифрования может быть реализовано выделением отдельного криптонабора, явно указывающего на отсутствие шифрования. При наличии шифрования оно осуществляется между узлом-отправителем и узлом-получателем вне зависимости от topology сети передачи и наличия промежуточных узлов.

Для обеспечения имитостойкости пакета в протоколе IPlir предусмотрена возможность его имитозащиты. Имитозащита пакета подразделяется на сквозную и транзитную. Сквозная имитозащита пакета осуществляется между узлом-отправителем и узлом-получателем и является обязательной. Транзитная имитозащита пакета осуществляется между парами соседних узлов в цепочке передачи пакета и является опциональной.

Для отдельного обеспечения конфиденциальности и имитостойкости пакетов могут использоваться как отдельные алгоритмы шифрования и имитозащиты, так и AED-алгоритмы.

### 6.2 Криптографические ключи

Подразумеется, что существует ключевая система, которая обеспечивает взаимодульствуящие узлы необходимыми ключами обмена и следует за синхронизацией этих ключей. Допускается как ручное, так и автоматическое управление ключами. Структура и вид конкретной ключевой системы выходят за пределы конкретных ключевых систем в настоящих рекомендациях предполагается, что ключи обмена, необходимые для защиты конкретного пакета, со всеми их обязательными атрибутами (метаинформацией) доступны на момент начала обработки пакета.

Для корректного функционирования протокола IPlir подразумеваются наличие системы уномерации узлов, в которой каждому узлу присваивается уникальный идентификатор. При этом заданной паре узлов и заданному криптографическому набору соответствует отдельный ключ обмена, индексировый пары идентификаторов этих узлов и номером криптографического набора. Допускается использование ключевых систем, в которых для заданной пары узлов и заданного криптографического набора предусмотрено существование нескольких ключей обмена одновременно (не более 16). Для обеспечения данной возможности каждый ключ обмена в протоколе IPlir дополнительно индексируется целочисленным значением от 0 до 15, размещаемым в поле KN или поле TKN IPlir-сообщения и позволяющим одним однозначно определить ключ обмена для заданной пары узлов и заданного криптографического набора.

Особенностью протокола IPlir является то, что для каждого IP-пакета на основе ключей обмена выработываются ключи шифрования пакета, сквозной имитозащиты пакета и транзитной имитозащиты пакета, используемые в соответствующих криптографических алгоритмах. Ключи шифрования пакетов, сквозной имитозащиты пакетов и транзитной имитозащиты пакетов, выработаемые для одного и того же IP-пакета, должны быть различными, за исключением случая использования AED-алгоритмов, в которых для шифрования и сквозной имитозащиты пакета применяется один ключ шифрования и сквозной имитозащиты пакета.

Ключ обмана (на основе которого выработываются ключи шифрования), пакет и сквозным имитозащиты пакета (или ключ шифрования и сквозной имитозащиты пакета), определяется значением поля KN IPlir-сообщения, идентификаторами узла-отправителя и узла-получателя и номером криптографического набора. Ключ обмена, на основе которого выработывается ключ транзитной имитозащиты пакета, определяется значением поля TKN IPlir-сообщения, идентификаторами взаимодульствуящих (транзитных) узлов и номером криптографического набора.

6.3.1.3 Algorithms for generating keys

A key for encryption and decryption of the packet $K_{\text{AEAD}}$ of length 256 bits is calculated as follows:

$$
K_{\text{AEAD}} = K_1 \parallel K_2 \parallel K_3 \parallel K_4,
$$

where each value $K_j \in V_{64}$, $j=1, 2, 3, 4$, is calculated in accordance with ГОСТ 34.12—2018 («Магма») in the regime of encryption generation according to ГОСТ 34.13—2018, that is:

- In place of the key is used a single key exchange, corresponding to the designated (transit) destination and source address, as well as the value of the IPir-configuration $KN$;
- In place of data is used a double-strace type
  $$
  \text{IntToVec}_8(i) \parallel \text{Label} \parallel aL \parallel I_{\text{KDF}} \parallel \text{SN} \parallel \text{Node} \parallel cL \parallel oL,

  where

Все числовые значения приведены в шестнадцатеричной записи. Нижний индекс в записи числа обозначает основание системы счисления. В системе счисления двоичные строки из $V^*$, длина которых кратна 4, записываются в шестнадцатаричном виде, а символ конкатенации («||») опускается, т. е. строка $a \in V_4$ будет представлена в виде $a_{r-1} a_{r-2} ... a_0$, где $a_i \in \{0, 1, ..., 9, a, b, c, d, e, f\}$, $i = 0, 1, ..., r-1$. Соответствие между двоичными строками длины 4 и шестнадцатаричными строками длины 1 задается естественным образом (см. таблицу А.1).

Для возможности записи в шестнадцатаричном виде двоичных строк, длина которых не кратна 4, каждая такая строка предварительно дополняется нулями слева в количестве, минимально необходимым для получения двоичной строки, длины которой кратна 4. Преобразование, ставящее в двоичную строку длину 4 $g$ шестнадцатаричную строку длины $r$, и соответствующее обратное преобразование для простоты записи опускается.
